# jolt-cpp: the program image and code come from segments, a16z's from sections (proofs can fail verification)

**Component**: `src/tracer/loader.cpp` (`_load_elf`), `compressed_trace_gen.cpp`, `isa/virtual.cpp`
(`VirtualBytecode::from_riscv_code`), `transcode.cpp` (the JIT's code scan). jolt-cpp `88dca85` (same behaviour at `821e1bd`).

**What happens.** jolt-cpp loads PT_LOAD segments, takes the one executable segment as the code, and decodes all of
it into bytecode. a16z's `jolt_program` (which every jolt-cpp proof is verified against, through `third-party/jolt` at
`7189216`) builds the image from sections: every section at or above 0x8000_0000, `program_end` the highest section
end, and only the Text sections decoded (`crates/jolt-program/src/image/elf.rs:40-110`). When the executable segment
holds anything that isn't a Text section, the two differ:

1. **Load failure** (reproducer `d1_rodata_in_text`: `.text` then an 8-byte `.rodata` of 0xff, one R-E PT_LOAD): the
   JIT aborts, "failed to decode risc instruction at 0x80000010"; a16z and meshsim's gold trace 4 rows.
2. **Silent bytecode mismatch** (reproducer `d1_decodable_gap`: `.text`, a jump over a `.rodata` of four `nop` words,
   `.text.b`, one R-E PT_LOAD): rows are identical in all three, but jolt-cpp decodes the four words as code, so
   `.text.b` (0x80000018) is bytecode index 7 of 11 in jolt-cpp and 3 of 7 in a16z. Every index after the gap is off
   by four; a proof built from jolt-cpp's bytecode fails verification against a16z's preprocessing, with no error before.

The same split affects the initial memory (jolt-cpp copies segment file bytes, a16z section data) and `program_end`
(hence the stack, heap and the image extents), wherever segments and sections don't coincide.

**Reproducers**: meshsim `wip/gold/test/guests/{d1_rodata_in_text,d1_decodable_gap}` (generated by `make_guests.py`).
`row_dump --index-of=0x80000018` and `upstream_rows --index-of=0x80000018` (jolt-asic-planning `worker18-rows`,
`worker18-upstream`) print each side's index.

**Expected**: the image, initial memory, `program_end` and code ranges as a16z's `decode_elf`.
**Fix**: jolt-asic-planning branch `worker18-fix-d1-sections` (`7b91e8a`, from `tracer-standalone-main` `fa59d9a`,
jolt-cpp 88dca85; `WORKER18/fixes/jolt-cpp-d1-sections.patch`): `_load_elf` builds the image by sections (each section
at or above 0x8000_0000 into RAM, `program_end` the highest section end, the initialized extents from section data,
the merged Text ranges recorded in `ProgramImage::text_ranges`); the JIT, `from_riscv_code` and the host I/O scan
decode a code image in which bytes outside the Text ranges are zero, so they get no bytecode entry (as in a16z) while
guest RAM keeps their contents. Results: `d1_rodata_in_text` loads, rows equal a16z's; `d1_decodable_gap` puts
`.text.b` at index 3 of 7, a16z's; EVM Zone and Cyclone (small inputs and 2^29) and seven example guests keep their run
hashes, layout and bytecode size.
